导读：为什么 MoE 的“推理”是另一个世界

如果把 MoE 模型看成一家医院：总参数是全部科室，激活参数只是每个病人实际挂到的几个号。训练关心的是“怎么让 256 个科室都得到足够的病人”，推理关心的却是完全不同的一组问题：病人来得快不快、挂号台会不会堵、跑腿送病历的走廊够不够宽、夜里值班的科室要不要关灯省电。

MoE 把参数容量与每 token 的计算量解耦了，但没有把显存、带宽和通信解耦。一个总参数 671B、每 token 只激活 37B 的模型，权重仍然要占 671B 的存放空间；每层专家分在不同 GPU 上，token 就要跨卡“跑腿”。于是推理系统的瓶颈沿着一条清晰的路线迁移：容量 → 路由 → 通信 → 显存 → 带宽 → 精度 → 调度 → 存储。这份综述按这条路线组织。

我们检索了 arXiv 上 2,357 篇与 MoE 推理/部署相关的候选，按主题相关性、时效性与工程信息密度打分，精读 59 篇、速览 96 篇。全文分成十章：先建立成本模型，再依次讨论通信、负载均衡、分离式部署、量化与 kernel、卸载与内存层级、边缘协同、投机与预取、服务系统与配置、硬件协同与可靠性。每篇精读论文都给出“问题—机制—原文数字—结论”四段式卡片，所有数字都能在原文中查到。

01

全景：MoE 推理的三堵墙

参数与计算解耦之后，容量、带宽、通信成为新的成本中心

MoE 把“模型有多大”和“每个 token 算多少”拆成了两件事。一个总参数 671B、每 token 只激活 37B 的模型，训练算力按 37B 付，但部署时 671B 的权重一个字节都不能少。这就像一家有 256 个科室的医院：病人一次只挂 8 个号，可是每个科室都得有医生、有房间、有设备。训练关心的是“怎么让每个科室都排到病人”，推理关心的却是另一组问题：病人来得快不快、挂号台会不会堵、送病历的走廊够不够宽、夜里值班的科室要不要关灯。

这份综述只讨论后者。我们把 MoE 推理的成本拆成三本账：容量账（权重必须全部存放）、带宽账（每 token 要读出激活的专家）、通信账（token 要跨卡去找专家）。三本账互相牵制：想省容量就得量化，量化会改变带宽；想省通信就得把专家放近，放近又受容量限制；想均衡负载就得复制或迁移专家，迁移本身又要花带宽。

先建立一个判断：decode 是带宽问题，不是算力问题。 每生成一个 token，模型要把激活的专家权重从显存读一遍，每读一个字节只做大约两次浮点运算（一次乘、一次加）。这意味着算术强度只有几个 FLOP/byte，远低于现代 GPU 的 roofline 拐点。数据中心 GPU 的拐点很高：H100 大约需要 140–150 个并发用户才能把算力“喂饱”，B200 更高。MoE 把这个问题放大了一个稀疏比：DeepSeek-R1 有 256 个专家、每 token 选 8 个，有效算术强度要再除以 32，于是需要约 4,480 个并发用户才能达到拐点——而一个 8 卡节点的 KV cache 在 32K 上下文下大约只能容纳 2,200 条序列。

结果就是一组很刺眼的数字：DeepSeek-R1 在 8 卡节点上大约只有 0.6% 的模型 FLOPs 利用率（MFU），单用户时降到约 0.03%；只有把专家铺到 144 张 H800（EP144，每卡约 2 个路由专家）上，聚合成千上万用户，MFU 才回到 20–25%。这不是实现问题，而是芯片的 F/B（算力/带宽）与 F/S（算力/容量）两个固定比例决定的物理约束。

工匠笔记

工匠笔记：不要用 FLOPs 判断推理成本。 训练看的是总算力，推理看的是“每 token 要搬多少字节”。一个 MoE 模型的 FLOPs 可能只有稠密模型的几分之一，但它的权重容量和跨卡通信可能贵一个数量级。做容量规划时先问三个数：总权重多大、每 token 激活多少、EP 跨多少跳。

把时间轴拉长看，MoE 推理的优化史就是一部“瓶颈迁移史”。2022 年的 DeepSpeed-MoE 和 Tutel 关心的是“怎么让专家并行跑起来、怎么让动态负载不拖垮流水线”；2024 年的 DeepSeek-V2 用 MLA 把 KV cache 压掉 93.3%，把长上下文推理的成本从 KV 转移到低秩 latent；2024 年底的 DeepSeek-V3 用无辅助损失的负载均衡、DualPipe、FP8 和节点受限路由，把 671B 模型的训练压到 2.788M H800 小时；2025–2026 年的工作则集中在更细的层面：all-to-all 的固定开销、专家放置的在线决策、Attention/FFN 的解耦、量化与 kernel 的融合、卸载与预取、以及“一个 rank 挂了怎么办”。下面十章按这条路线展开。

01

DeepSpeed-MoE: Advancing Mixture-of-Experts Inference and Training

2201.05596·2022·arXiv

问题MoE 能省训练算力，但参数效率低、推理系统不适配，导致“训得起、部署不起”。

机制提出 PR-MoE（金字塔-残差 MoE）：把稠密 MLP 与一个专家并联，专家作为稠密分支的误差修正项，在 top-1 通信量下接近 top-2 的泛化；只在最有效的层放专家，并用金字塔式专家配置压总参数。再用分阶段 MoE-to-MoE 蒸馏得到 Mixture-of-Students（MoS）。推理侧构建专家并行 + 多 GPU 扩展的 DeepSpeed-MoE 推理系统。

  • PR-MoE 最多减少参数 3×，质量不变（基线：同等质量原 MoE）
  • MoS 最多减少模型大小 3.7×（基线：PR-MoE）
  • 推理系统延迟/成本改善 7.3×（基线：已有 MoE 推理方案）
  • 相比质量等价稠密模型，推理快 4.5×、成本低 9×
  • 万亿参数 MoE 推理延迟低于 25 ms
  • 训练达到 6.7B 稠密质量只需 1.3B 的训练算力（5× 节省，128×A100）

结论核心洞见是“参数效率”而非单纯稀疏性决定推理可行性；残差专家 + 蒸馏是有效的压缩路径。局限是结论建立在自建 NLG 模型与自家系统上，正文对推理系统内部调度展开不足。

Tutel: Adaptive Mixture-of-Experts at Scale

2206.03382·2022·arXiv

问题MoE 的 token 路由使每个专家负载在运行时动态变化（实验中单次训练负载变化可达数量级），静态并行与静态流水线无法适配。

机制让 MoE 参数分布与输入数据分布采用“同一套 layout”，任何并行/流水线方案都可直接复用，不产生数学不等价或张量迁移开销，从而运行时零成本切换。在此基础上做自适应流水线（按 capacity factor 分桶、在线搜索策略）与自适应并行切换；通信侧提出二维层次（2DH）All-to-All：先节点内、再节点间，配合 stride memcpy 重排与 flexible All-to-All 避免 rigid output layout，再用 MSCCL 自定义编译器优化。

  • 单 MoE 层相对 Fairseq 加速 4.96×（16×A100）与 5.75×（2,048×A100）
  • SwinV2-MoE 端到端训练最高 1.55×、推理最高 2.11×（基线 Fairseq，128 GPU）
  • 两种静态并行方案在不同负载下性能差距 7.39%–27.76%
  • All-to-All 开销占比 33.7% / 46.3% / 56.7%
  • 2,048 GPU 上 layout 变换后 matmul 仅达前者 8.8% 吞吐
  • 自适应流水线相比流水线度 1 最高提升 30% / 67%

结论把“动态负载”当作一等公民，用 layout 不变性换取运行时零开销自适应，是最有复用价值的系统思想；2DH 可扩展到 4,096 GPU，但大消息下因额外拷贝延迟更高，需要在线性/2DH 与协议间动态切换。

Accelerating Distributed MoE Training and Inference with Lina

2210.17223·2022·arXiv

问题分布式 MoE 中交错执行的 all-to-all 成为瓶颈：它同步阻塞计算、与 allreduce 争抢带宽、传输量随专家数线性增长。

机制先剖析三大成因：单层单次迭代需 4 次 all-to-all；反向传播中 all-to-all 与 allreduce 并发共享带宽；传输字节随专家数线性增长。再做张量分区，把梯度切成等大小 chunk 形成 micro-op，用优先级调度保证 all-to-all 独占带宽、allreduce 只在空隙推进，并让专家计算与 all-to-all 流水重叠。再做 expert packing：单卡放多个专家以减少跨设备传输，配合多 FFN 并行（利用专家 FFN 约 35% 的空闲 SM）与 DRAM offloading。

  • 训练 step time 最多降低 1.73×，95% 分位推理时间平均降低 1.63×
  • all-to-all 平均占 step time 37.4%，期间 GPU SM 效率仅 3.7%
  • 专家数 2→16 时 all-to-all 占 step time 从 33.4% 升到 44.5%
  • micro-op 调度使梯度 allreduce 快 6.6 ms（21.7%）
  • expert packing 使 MoE 层完成时间 18.7→13.7 ms（32.1%）
  • GPU 利用率 69%→85%，FFN 平均占用率 36%→67%（16 专家）

结论把 all-to-all 从“被动等待”变为“被优先保障的阻塞操作”，再用 packing 配平计算与通信；收益高度依赖拓扑（2/8 专家增益最大，4/16 专家仅约 1.37–1.47×），最优分区大小需逐例调参。

DeepSeek-V2: A Strong, Economical, and Efficient Mixture-of-Experts Language Model

2405.04434·2024·arXiv

问题LLM 能力随参数增长，但训练算力与推理吞吐（尤其 MHA 的 KV cache）成为部署瓶颈；GQA/MQA 降 KV cache 会损性能。

机制注意力侧提出 MLA，对 key/value 做低秩联合压缩到 latent（KV 压缩维 512、query 压缩维 1536），并用解耦 RoPE 处理位置编码，使 KV cache 只存压缩 latent。FFN 侧沿用 DeepSeekMoE：160 个 routed 专家（中间维 1536）+ 2 个共享专家，每 token 激活 6 个 routed 专家；配套 device-limited routing（每 token 最多 3 台设备）、三组负载均衡损失与设备级 token dropping。部署时权重转 FP8，KV cache 平均 6-bit 量化。

  • 236B 总参数 / 每 token 激活 21B，上下文 128K，预训练 8.1T token
  • 相比 DeepSeek 67B：训练成本节省 42.5%，KV cache 减少 93.3%，最大生成吞吐 5.76×
  • 每万亿 token 训练：300.6K → 172.8K GPU 小时（H800）
  • 单节点 8×H800：生成吞吐 >50K token/s，prompt 输入 >100K token/s
  • MMLU 5-shot 78.5（DeepSeek 67B 71.3、Mixtral 8x22B 77.6）

结论用 MLA 把长上下文推理的成本从 KV cache 转移到低秩 latent，再用细粒度 + 共享专家把训练算力压到 21B 激活水平；基础英文能力仍略逊于 LLaMA3 70B（英文 token 不足其 1/4）。

DeepSeek-V3 Technical Report

2412.19437·2024·arXiv

问题在追求前沿能力的同时把超大规模 MoE 的训练与推理成本压到可承受范围，并解决负载均衡损失损害质量、流水线气泡、跨节点 all-to-all 与 FP8 精度不稳。

机制延续 MLA + DeepSeekMoE（61 层、hidden 7168、1 个共享专家 + 256 个 routed 专家、每专家中间维 2048、每 token 激活 8 个）。负载均衡改为 auxiliary-loss-free：用可学习 bias 调整路由偏好（前 14.3T token 速率 0.001，最后 500B 设为 0），辅助损失仅保留 0.0001。训练加入 multi-token prediction（深度 1）。系统侧 DualPipe 双向流水线减少气泡并用计算-通信重叠隐藏通信；定制跨节点 all-to-all kernel，利用 IB 与 NVLink 带宽差，每 token 最多送 4 个节点，仅用 20 个 SM 跑满带宽。精度侧 FP8 混合精度：激活 1×128 tile、权重 128×128 block 缩放，统一 E4M3，在线算 scale，MoE 激活以 FP8 缓存与分发，优化器状态 BF16，并用高精度累加补偿 FP8 GEMM。

  • 671B 总参数 / 每 token 激活 37B，预训练 14.8T token
  • 全流程 2.788M H800 GPU 小时（预训练 2664K + 上下文 119K + 后训练 5K），约 $5.576M
  • 每万亿 token 预训练仅需 180K H800 小时（2,048 卡 3.7 天）
  • FP8 相对 BF16 损失误差始终 <0.25%
  • H800 上 FP8 GEMM 累加精度仅约 14 bit；K=4096 时最大相对误差接近 2%
  • 每节点平均 3.2 个专家，20 个 SM 即可跑满 IB+NVLink
  • MMLU 5-shot 87.1（V2 78.4、LLaMA-3.1 405B 84.4）
  • 训练全程无不可恢复 loss spike，未做 rollback

结论以 2.788M GPU 小时取得与领先闭源模型可比的性能，说明“算法-框架-硬件”协同设计能把通信与精度开销同时压住；代价是 DualPipe 保留两份参数、FP8 依赖细粒度缩放与高精度累加，工程门槛高。

Insights into DeepSeek-V3: Scaling Challenges and Reflections on Hardware

2505.09343·2025·ISCA '25

问题LLM 规模化暴露硬件三重约束——显存容量、计算效率、互连带宽；论文从硬件与模型双视角分析 V3/R1 如何在仅 2,048 张 H800 上实现低成本训练与推理，并给出下一代硬件建议。

机制MLA 把 KV 压缩为 latent，显著降低每 token KV cache；MoE 用“总参数大、激活参数小”换取算力-通信折中；FP8 用 1×128 tile（激活）与 128×128 block（权重）细粒度量化配合高精度累加。互连侧做硬件感知的 node-limited routing：H800 的 scale-up（NVLink 实测约 160 GB/s）与 scale-out（每 NIC 50 GB/s、有效约 40 GB/s）带宽比约 4:1，因此限制每 token 最多选 4 个节点以压 IB 流量，并用 DeepEP 实现 >40 GB/s 的 all-to-all。集群侧提出 Multi-Plane Fat-Tree；MTP 用单层轻量头并行验证后续 token。LogFMT 通信压缩因 encode/decode 开销 50%–100% 未采用。

  • 每 token KV cache：V3（MLA）70.272 KB；Qwen-2.5 72B（GQA）327.680 KB（4.66×）；LLaMA-3.1 405B 516.096 KB（7.28×）
  • 每 token 计算量：V3 约 250 GFLOPS；Qwen-72B dense 394；LLaMA-405B dense 2448
  • MTP 第二个后续 token 接受率 80%–90%，TPS 相比无 MTP 提升 1.8×
  • EP 并行下 token 以细粒度 FP8 分发，通信量比 BF16 减少 50%
  • H800 NVLink 带宽由 900 降至 400 GB/s；NVLink 200（实测约 160）、每 NIC 50（有效 40），约 4:1
  • Multi-Plane Fat-Tree：2,048 端点 $9M（$4.39k/端点）；65,536 端点 $491M（$7.5k/端点）

结论这是一篇“反向设计”文献：把 V3 的每个架构选择回溯到具体硬件瓶颈（KV 容量、4:1 带宽比、FP8 累加位宽），并据此提出精确低精度计算单元、scale-up/scale-out 收敛、低延迟 fabric 等方向；结论带有强硬件绑定，迁移到其他拓扑需重新配平。

这六篇构成了理解后面所有工程取舍的底座：DeepSpeed-MoE 说明“参数效率”决定推理可行性；Tutel 与 Lina 说明动态负载与 all-to-all 是系统层的第一性问题；DeepSeek-V2/V3 说明模型架构（MLA、细粒度专家、共享专家、节点受限路由）可以把系统问题前移到设计期解决；Insights 则把每个选择还原成硬件比例。后面的通信、均衡、解耦、量化、卸载，本质上都是在补这三本账里剩下的缺口。

02

通信与专家并行：把 all-to-all 藏起来

dispatch/combine 的固定开销、拓扑层级与 kernel 融合

专家并行（EP）把每层专家分到不同 GPU 上，于是每个 MoE 层都有两次 all-to-all：dispatch 把 token 送到持有其专家的卡，combine 把专家输出送回 token 的源卡。这两步在关键路径上，实测可占 MoE 层延迟的 40%–47%。更麻烦的是小 batch 下的固定开销：每卡只有几个 token 时，真正要传的字节在 NVLink 上不到 1 微秒，但一次 dispatch+combine 往返要几十微秒——时间花在生产者与消费者之间的同步、元数据交换、以及“先写中间缓冲、再拷贝/重排”的额外一过。

于是通信优化分成三条路线：减少固定开销（one-sided 直写、用数据本身当标志、把 dispatch 融进 kernel）、减少传输量（rank-major 布局、去重、分层聚合、组播/网内集合通信）、以及把通信藏进计算（细粒度流水、SM 分区、band pipeline）。

INC-MoE: Overlapping In-Network Collectives and Expert Computation

2610.36339·2026·arXiv

问题多节点 EP 中 dispatch/combine 位于关键路径，跨节点带宽远低于节点内，通信可主导层延迟；仅把集合通信卸载到交换机并不够，因为单个集合仍只占一个链路方向。

机制把 dispatch 表达为网内 AllGather（交换机侧组播）、combine 表达为网内 ReduceScatter（交换机侧归约），两者加载链路相反方向，因此并发执行可把带宽受限时间从 2(N−1)/N 降到 (N−2)/(N−1)（4 rank 33%、8 rank 43%）。在单持久 kernel 内把 token 切成 band，做 AllGather–FFN–ReduceScatter 三段流水，角色专用 thread block 同时处理相邻 band。

  • OLMoE prefill、4-way EP、模拟 4 节点：TTFT 降低 20.2%–33.1%，吞吐提升 25.3%–49.5%
  • 并发 AG+RS 等效带宽 163–172 Gbps vs ring 约 130 Gbps（+25.6%–31.8%）
  • per-token cosine 与基线一致
  • 每 rank 有效 100 Gbps（400 Gbps 共享链路）

结论网内集合通信与 kernel 级 band 流水是互补的：前者省带宽，后者把两个方向同时用满；局限是依赖可编程交换机，当前为模拟器验证。

工匠笔记

工匠笔记：先分清“带宽受限”还是“固定开销受限”。 大 batch/prefill 时，优化目标是少传字节、用满链路（分层聚合、组播、去重）；小 batch/decode 时，优化目标是少一次同步、少一次元数据交换、少一个 kernel（one-sided、Sentinel、单 kernel 融合）。同一套通信库在两个区间的最优参数往往相反。

这一章的八个系统给出了一条清晰的收敛路线：从“多 kernel + host 编排”走向“单 kernel + 设备发起”，从“先写缓冲再重排”走向“就地读/直写”，从“全局屏障”走向“数据即标志”。分歧在于“一个 kernel 还是两个 kernel”：FlashMoE/MonoMoE 主张全融合，GC-MoE 用 Green Contexts 把通信与计算拆成两个并发 root，Weave 则在 megakernel 内做逐层动态 SM 划分。本质是同步域大小与资源隔离的取舍，没有普适答案。

2609.21483·2026·arXiv

问题EP 下每层 MoE 都是带昂贵 dispatch/combine 的分布式计算（可占层延迟 40%）；现有重叠方案在空间上浪费——最优通信/计算 SM 比例由每层路由结果决定且逐层逐 GPU 变化，固定策略（DeepEP 固定 20/132 SM、ParallelKittens 编译期固定）或粗粒度动态（Comet 按迭代）都会错配；时间上 up-GEMM 必须等 dispatch 送达 token、combine 必须等 down-GEMM 完成，导致通信 SM 在中间计算阶段空转形成气泡。

机制在 persistent megakernel 内置轻量 cost model——routing 一完成，每层通信量（按去重后的远端 token 数，同一远端 token 只跨网一次并被多个选中专家复用）与计算量即已知；spatial scheduler 据此把 SM 划成 communication workers 与 computation workers 以匹配吞吐比，temporal scheduler 进一步协调两组，用“steal tiles”让计算 worker 在通信窗口内接管 tile、填掉气泡，目标是最小化 SM 空闲。调度粒度是 per layer、per GPU、运行时决定。dispatch 侧 token 去重融进 megakernel：comm tile 事先知道 token 是否重复，若是则直接读首次传输填充的本地 HBM buffer。

  • 4×H100 SXM、6 个主流 MoE 模型，相对 5 个 SOTA 基线：MoE 层几何平均 2.89×，端到端几何平均 1.33×
  • 6 模型×3 序列长度（2k/4k/8k）共 18 个配置，每层延迟均最低
  • 单层内 per-GPU 最优通信 SM 数在 DSv2 上跨度 12–36
  • DSv2-Lite、seq=2048、EP=4：SM Active 91%、comm-comp overlap 47%；Comet 14.3%、DeepEP 9.2%、PK 5.8%、TD 5.1%
  • cost model 与穷举最优平均差距 8.2%；在线开销约 0.021% 层时间

结论把“SM 分区”从编译期/迭代级推进到逐层逐 GPU 的运行时决策，并首次同时处理空间错配与时间气泡；局限是 cost model 仍差 8.2%，实现绑定 ParallelKittens 与 BF16、单节点 EP=4。

工匠笔记

工匠笔记：先问“这一层到底在等什么”。 decode 小 batch 时等权重流（提高带宽利用率、消除 padding、把辅助 kernel 藏进主 kernel）；prefill 大 batch 时等 GEMM/通信（tile 填满、负载均衡、SM 分区）；量化只有在“权重流是瓶颈”时才直接换成速度，否则只是省显存。把这三个区间混为一谈，就会得到“量化了但没变快”的结果。

这一章的分歧在于“精度—吞吐权衡的位置”：GC-MoE 用 FP8 激活 + FP4 权重并声称与 BF16 cosine 一致；MonoMoE 停留在 E4M3 FP8；JSQ 走 paired NVFP4 W4A4 + 稀疏，代价是 96.09% 保留率与 AIME25 掉 11 分；ExactMoE 用 W4A16 换 99.23% 准确率但 16-slot 下比 BF16 慢 18.1%。共同点是“只量化专家、保留 router/attention 高精度”，分歧在于是否接受可测量的精度损失换取更大压缩。

卸载与内存层级：用带宽换容量

专家缓存、预取、量化搬运与 HBF

当模型装不进显存时，最直接的办法是把不活跃的专家放到 CPU DRAM 或 SSD，按需搬进来。代价是 PCIe/NVMe 的带宽比 HBM 低一到两个数量级：Mixtral 单专家 16-bit 权重超过 300 MB，从 CPU 搬一次约 50 ms，而 GPU 上算一次只要约 3 ms。于是所有卸载系统的核心问题都变成同一个：能不能提前知道下一个 token 要用哪些专家，把搬运藏进计算。

机制以 batch=1 的高激活稀疏性为前提，做“激活感知的专家卸载”。(1) 序列级激活追踪：为每条序列记录 Expert Activation Matrix（EAM，层×专家的激活 token 数），并用 EAMC 集合构建算法挑选代表不同激活模式的 EAM；(2) 预取：用当前序列 EAM 与 EAMC 中最相似 EAM 做距离匹配得到预测 EAM，优先级 = 预测激活比例 × 层距离衰减 (1 − layer_idx/n_layers)，每过一个 MoE 层刷新一次（continuous refinement），带宽富余时可预取更深层；(3) 缓存替换同样用“激活比例×层衰减”打分；(4) 系统层做原子内存拷贝、NUMA 内存池、多 GPU/EP。

  • switch-base-128、RPS=0.5：99 ms；ZeRO-Infinity/Offload >20 s，PyTorch-UM 366 ms
  • nllb-moe-128 尾延迟比 PyTorch-UM 好 22.1×，按需取数少 67%；batch 1 326 ms、batch 64 1.81 s（PyTorch-UM 15.38 s）
  • 预取准确率（256 专家/层）：55% vs Traced-TopK 34% vs TopK 7%；128 GB/s 下 switch-large-128 38%→98%

结论在 batch 很小的单用户场景把专家搬运延迟基本藏住，并把部署成本压到单 GPU 量级；整套收益建立在“低 batch + 强时序局部性”上，batch 增大后预测与缓存效果明显退化。

Fiddler: CPU-GPU Orchestration for Fast Inference of MoE Models

2402.07033·2024·arXiv

问题单张 24GB 消费级 GPU 跑不压缩的 Mixtral-8x7B（>90GB，16-bit），纯卸载方案把 300MB 级专家权重经 PCIe 搬进 GPU，通信开销远超计算。

机制把 CPU 当“算力”而不只是“仓库”。缺失专家时不搬权重，而是把激活（远小于权重）从 GPU 拷到 CPU，在 CPU 上算完专家再拷回激活，从而把 CPU-GPU 通信量压到最小；只有当 batch 大到 CPU 计算时间超过权重搬运时间时才切回 GPU 执行。初始化时非专家层（Mixtral 中 <2B 参数）常驻 GPU，其余按校准数据（ShareGPT）统计的专家热度顺序尽量多放热门专家到 GPU 以提高命中率；prefill 阶段用“GPU 执行时间视为常数、CPU 执行时间随 token 数线性增长”的模型求解最优专家放置/执行配置。

  • 单 batch 推理 1.26×、长 prefill 1.30×、beam search 11.57× 加速
  • 单张 24GB GPU 可让 >90GB 的 Mixtral-8x7B 生成（正文具体 tok/s 被剥离）
  • 单专家 16-bit 权重 >300 MB；CPU→GPU 拷贝一次约 50 ms（Quadro RTX 6000 / L4）
  • 相对现有卸载方法“一个数量级”的提升（正文多处数字被压缩文本吞掉）

结论在小 batch、延迟敏感的本地下，把专家放到 CPU 上算优于搬运权重，且在单 batch、长 prefill、beam search 三种场景都不退化；局限是假设非专家层能放进 GPU、依赖校准集热度，batch 变大后 CPU 计算成为瓶颈。

HOBBIT: A Mixed Precision Expert Offloading System

2411.01433·2024·arXiv

问题边缘设备（如 32GB Jetson AGX Orin）装不下 Mixtral-8x7B 的 87GB 权重；专家加载主导推理时间（RTX 4090 上约 85.5%，Jetson Orin 上约 94.5%），而现有卸载要么加载慢、要么靠跳专家损精度。

机制用“混合精度替换”把 cache miss 的代价降下来，并按 MoE 计算层级分三层设计。(1) token 级动态加载：用门控输出幅值近似专家重要性（与专家输出幅值的 Pearson 相关系数 0.99），设两个阈值把专家分为高精度 67%、低精度 30%、跳过 3%；命中缺失时按分数决定取 fp16、int4 还是跳过，int4 替换 fp16 最高带来 4× 加载加速。(2) 层级自适应预取：利用残差导致的相邻层门控输入高相似度，用当前层门控输入预测后续层所需专家，下一层 top-1 预测准确率平均 96%，下两三层约 90%。(3) 序列级多维缓存：提出 LHU（least hit usage）替换策略，按“精度版本 × miss 惩罚”而非单纯频率计分。

  • 相对 SOTA 卸载系统解码最高 9.93× 加速
  • Jetson AGX Orin：相对 Llama.cpp 解码平均 13.0×（Mixtral）/18.9×（Phi-MoE），prefill −79%/−80%；相对 MoE-Infinity 解码 3.64×/9.93×
  • RTX 4090：相对 MoE-Offloading 解码 3.21×/3.29×；相对 MoE-Infinity 2.30×/3.92×
  • 精度：Mixtral GSM8K 0.52→0.51，Phi-MoE 0.83→0.82，所有模型下降 ≤1%
  • 动机：10% 专家跳过率使 PPL 上升 >1%；Mixtral 单层 CPU→GPU 加载约 80 ms，RTX 4090 计算仅约 3 ms

结论以“低精度替换而非跳过”保住精度（≤1% 下降），同时把加载量降下来，在边缘端收益最大；阈值需按模型 profile 标定，方案强依赖边缘设备的 CPU/SSD 带宽特征。

F/B、F/S、wafer-scale 与 mutable membership

最后回到硬件。主流 GPU 是“算力重、容量轻”的：算术吞吐极高，但显存装不下现代模型。decode 只需要很少的算力和很大的容量，于是 GPU 的浮点单元在 decode 时只有个位数利用率，而你为容量买的每一 GB 都捆绑了更多用不上的算力。论文用两个固定常数刻画这种错配：F/B（roofline 拐点，决定算力能不能被用上）与 F/S（每 GB 容量捆绑的算力，决定你必须买多少算力）。

按这两个比例，出现了三类设计点：数据中心 GPU（高 F/B、高 F/S，需要上千并发才有效率）、内存丰富的消费设备（低 F/S，但容量仍不够）、以及专用 decode 加速器（低 F/B、低 F/S、故意用更便宜的低带宽 DDR5）。另一条路是把互联做成晶圆级：wafer-scale chip 用 mesh 网络把数百 die 连成统一域，E/D（专家数/设备数）可以降到 1，但 mesh 的冷热链路不均与无片上磁盘又带来新的迁移问题。

可靠性则是另一个维度：wide EP 让每个 decode step 都依赖所有 rank，一个 rank 挂掉就可能让整个实例不可用。传统做法是重启整个实例（348 秒），而正确的做法是把 membership 变成可变的运行时状态，原地收缩、修复专家覆盖、再增量恢复。

Surviving Partial Rank Failures in Wide Expert-Parallel MoE Inference

2605.10670·2026·arXiv

问题wide EP 让每个 decode step 依赖所有 rank，一个 rank 失败就可能中断整个服务；现有 EP 栈把 membership 当初始化时固定的配置，同一 rank 集决定 communicator 状态、专家放置与烧进 CUDA graph 的路由元数据，无法在故障后收缩而保持实例有效。

机制把部分故障容错表述为“live EP validity”问题：一个 EP 实例有效需同时满足 peer 可达、专家覆盖完整、执行状态一致。EEP 把 membership 表示为显式、可变的运行时状态，只修复被故障破坏的那部分状态：恢复 peer 可达而不重建通信底座；用带宽感知的层次结构修复丢失的专家覆盖；让修复后的 rank 重新加入而不迫使健康 rank 重捕 CUDA graph。专家备份可选：每节点在 pinned CPU DRAM 预放一部分专家权重（671B 模型四节点各约 167.5 GB）。

  • 稳态服务距固定 membership 的 DeepEP 基线 4.4% 以内（prefill-heavy 约 1.4%）
  • 单 rank 故障：11 s 恢复暂停 + 8 s 重加入暂停，52 s 内吞吐恢复到故障前 95%；固定 membership 全重启基线直到 348 s 仍不可用
  • 1/2/4/8/16 rank 故障：恢复约 6–11 s，第二次零吞吐窗口 4/6/9/15/15 s
  • 相对全实例重启改善 1–2 个数量级
  • 生产数据中心 GPU/节点故障占硬件故障 >78%，382 事件/月

结论局部 rank 故障不必变成整实例停机：把 membership 变成可变状态、只修复失效部分，可把数分钟停机压到十几秒；代价是 CUDA graph 与路由元数据需要支持原地重写，实现复杂。

工匠笔记

工匠笔记：可靠性要算进 SLO。 一个 32 卡 EP 实例挂一张卡，全重启 348 秒；按 99.9% 可用性算，这已经吃掉一个月的停机预算。wide EP 越大，单点故障的爆炸半径越大，所以“可收缩的 membership”不是可选项，而是大规模服务的基础能力。

十章走完，可以看到一条主线：MoE 推理的每一次性能提升，都是把某个“串行等待”变成“并行资源”——通信与计算重叠、专家放置与请求前瞻重叠、卸载 I/O 与投机计算重叠、扩缩容与 serving 重叠、故障修复与健康 rank 的执行重叠。下一步的瓶颈会继续迁移：当通信、显存、精度都被压到极限，剩下的就是调度粒度、可靠性、以及“为 decode 重新配比芯片”的系统经济学。
