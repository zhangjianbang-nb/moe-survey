一个关于 Mixture-of-Experts 的故事

小词的奇幻漂流

一家医院的十年 · 精读版

基于 100 篇论文 · 6 篇专业导读 · 2026 年 11 月

这个故事想讲清一件事：大模型为什么都开始"开医院"了。

你会跟着一个叫小词的 token，走进一座有 256 个房间的城堡，看它怎么被分诊、怎么跑腿、怎么遇上抢客人的风波——以及这座城堡十年里是怎么一次次把自己重新盖了一遍的。

这版怎么读

① 只想听懂 → 顺着故事读，跳过灰框。

② 想顺带学点硬的 → 每章开头的专业导读先看，再看故事。

③ 想深挖 → 每章的工匠笔记里有公式、数字和论文出处。

序

为什么讲这个故事Before We Begin

在讲小词的故事之前，先说三句话。

第一句：大模型变大的方式，十年前是"把每个工匠都练得更强"，现在是"雇更多工匠，但每个客人只见几个"。前者叫稠密模型，后者叫 MoE。

第二句：MoE 不是新东西。1991 年就有人提出，2017 年才变得可训练，2024 年才真正成为主流。它的历史，是一部"瓶颈搬家史"。

第三句：这十年里，几乎所有 MoE 论文都在回答同一个问题——"稀疏了以后，什么变贵了？"

专业导读 · 三分钟看懂 MoE

MoE 的唯一卖点：让"参数容量"和"每 token 计算量"脱钩。容量可以涨到万亿级，每个 token 的算力开销却只相当于一个几十 B 的稠密模型。

  • 稠密模型：每个 token 都要过全部参数。70B 稠密模型，每个 token 就是 70B 次乘加。
  • MoE：模型里有 N 个"专家"（各自独立的 FFN），门卫（router）为每个 token 挑 k 个。V3 是 256 个路由专家 + 1 个共享专家，top-8。
  • 换来了什么：V3 总参数 671B，每个 token 只用 37B —— 容量约 18 倍，算力与 37B 稠密模型相当。
  • 付出了什么：显存要装下全部 671B（BF16 下 1.3TB）；专家分散在不同设备上，token 要跨设备"换乘"（all-to-all）；负载不均会让部分专家闲置。
  • 一句话：MoE 把"记忆"和"思考"分开卖——记忆便宜（存得多），思考贵（算得少）。

参考：Shazeer et al., 2017 · DeepSeek-V3 Technical Report, 2024 · MoE 推理系统综述, 2026

下面这个故事，就是把上面这几条，拆成六章来讲。每一章前面都有一块"专业导读"，写给想看清数字和公式的你；故事本身，写给想先听个明白的你。两边说的是同一件事。

01

城堡The Castle

专业导读 · 路由与稀疏激活

MoE 的全部机制可以压缩成一个公式：y = Σi∈TopK gi(x)·Ei(x)。难点不在公式，而在三个选择：谁来选、选几个、怎么加权。

  • 1991 · Jacobs 等提出 "adaptive mixtures of local experts"：多个专家 + 一个门控网络，门控决定每个输入用哪些专家。想法诞生，但当时没有稀疏训练的手段。
  • 2017 · Shazeer 等的 Sparsely-Gated MoE 用 top-k 稀疏门控做到 137B 参数，第一次证明"只激活少数专家"能训得动。
  • 门控怎么算：一个矩阵 Wg 把 token 向量映射成 N 个分数（s = x·Wg），取最高的 k 个；选中专家的权重归一化后加权求和。
  • sigmoid 还是 softmax：V3 起改用 sigmoid——每个专家独立判断"我适不适合这个 token"，不与其他专家抢同一个分母。2025 年的理论分析（arXiv:2505.10860）证明这让路由专家的收敛速率从 n−1/4 提到 n−1/2。
  • V3 的规格：256 个路由专家 + 1 个共享专家，top-8；61 层，隐藏维度 7168；671B 总参数 / 37B 激活。

关键论文：Jacobs et al., 1991 · Shazeer et al., 2017 · DeepSeek-V3, 2024 · arXiv:2505.10860, 2025

从前，有一个叫小词的 token。

小词出生在一句话里。那句话是"这家医院治好了我的病"。小词就是"医院"这两个字——它一生的使命，是让读到这句话的人，想起消毒水、白大褂，和走廊尽头那盏彻夜不灭的灯。

每句话里都有很多小词，它们排着队，一个一个走进一座巨大的城堡。这座城堡叫 MoE 城堡。

城堡有多大？门口的石碑上刻着一行字：256 个房间，257 位工匠。小词数了三遍，也没数清多出来的那位住在哪儿。后来它才知道，那位工匠住在城堡最深处的一间小屋里，不挂招牌，但每个客人都要从他门口路过——他叫"全科门诊"。

城堡里有一条规矩，是全世界城堡里最奇怪的规矩：

城堡有 256 个房间，每个房间住着一位工匠。但每个客人只准进 8 个房间。

为什么要这样？因为很久以前，城堡只有一位全职工匠。那位工匠很厉害，什么都会做——数学、历史、写诗、看病，样样精通。可是每来一个客人，他就得把所有本事从头到尾使一遍。客人越多，他越累；累到最后，城堡的主人想再多雇点工匠，却发现——雇一个，累一倍。因为每一位新工匠，都要把全部本事重新使一遍。

这叫稠密：每个客人，都要经过每一位工匠。

于是聪明的建筑师想出了这个怪规矩：雇 256 个工匠，但每个客人只见 8 个。 这样，城堡的本事大了几十倍，可每个客人花的力气，一点没多。

这叫稀疏：每个客人，只惊动一小撮工匠。

小词第一次走进城堡时，门口站着一位笑眯眯的门卫。

"你好，"门卫说，"我叫路由器。让我看看你。"

门卫的眼睛在小词身上扫了一圈。那不是普通的眼睛——那是一面由 256 块小镜子拼成的墙，每一块镜子都从不同角度照小词：3 号镜子看它像不像数学题，17 号镜子看它有没有历史味，42 号镜子闻它身上有没有消毒水……

每块镜子给出一个分数。门卫飞快地在心里排了个序：

"嗯，你身上有股消毒水的味道。3 号房间、17 号房间、42 号房间……还有这 5 个，去吧。"

门卫递给小词 8 张房卡，每张卡上还写着一个数字——那是小词在这 8 个房间里的"分量"。8 张卡上的数字加起来，正好是 1。

小词揣着房卡，跑进城堡深处。8 个房间，8 位工匠，每人给它加工一遍：3 号房间的工匠把它的意思拧了拧，17 号房间的工匠又添了点料，42 号房间的工匠在它身上盖了个"病"字的戳……

小词把 8 份加工结果按房卡上的数字加权混合，变成一份新的小词，心满意足地走出城堡。

它回头看了一眼，忽然觉得：这座城堡不像一座城堡，倒像一家医院。每个房间是一个科室，每位工匠是一位专科大夫，而它自己——一个 token——是一个来挂号的病人。

工匠笔记 · 门卫到底在算什么

门卫不是一个真人，而是一个小矩阵 W_g。它把小词的向量乘一下，得到 256 个分数（s = x·W_g），然后取分数最高的 k 个房间。房卡上的"分量"是这 k 个分数的归一化结果，保证加起来等于 1。

DeepSeek 系列从 V2 起把打分函数从 softmax 换成了 sigmoid：softmax 让所有房间在同一个分母下互相抢分（一个高就压低其他所有），sigmoid 让每个房间独立判断"我适不适合这个客人"。

2025 年的理论分析（arXiv:2505.10860）证明，这让路由专家的收敛速度从 n−1/4 提到 n−1/2——同样的数据，学得更快。代价是"共享专家"必须存在：sigmoid 不再强制归一化，需要一个所有人都要经过的专家兜住通用知识。

这就是 MoE 的全部秘密。一句话：门卫分诊，客人跑腿，工匠加工，加权混合。

当然，故事到这里才刚开头。因为小词很快就发现，这座城堡有两件事，门卫没告诉它。

02

城堡的灯The Lights Are Always On

专业导读 · 显存与算术强度

MoE 省的是算力，不是显存。这是它最容易被误解的一点，也是推理系统所有麻烦的源头。

  • 房子有多大：671B 参数按 BF16（2 字节）存放要 1.3TB；一张 H800 只有 80GB，装下它至少要 16 张卡，还得给 KV cache 和激活留余量。
  • 为什么灯全亮：门卫无法预知下一个 token 会选哪些专家，所以全部专家必须常驻显存——不能按需换入换出。
  • 算术强度：decode 时每从显存读 1 字节权重，只做约 1 次乘加（BF16），即 1 FLOP/byte；H100 的"拐点"是 295 FLOP/byte。差近 300 倍，GPU 大部分时间在等显存。
  • 利用率：batch=1 时 GPU 算力利用率只有 1–2%；要让专家从"等内存"变成"等算力"，每个专家手头得攒约 256 个 token。
  • 三板斧：做大 batch、做专家并行、做量化——三者本质都是"把每字节权重摊到更多 token 上"。
  • 训练侧对照：V3 用 2.788M H800 小时训完 14.8T tokens，全程零不可恢复 loss spike——算力省到极致，显存和通信一分没省。

关键论文：DeepSeek-V3, 2024 · MoE 推理系统综述, 2026

可是小词不知道，城堡有个它看不见的秘密。

每天夜里，城堡 256 个房间的灯，全都亮着。

没有客人的房间，工匠也坐在里面，灯也亮着，火也烧着。小词有一次半夜路过，忍不住问一位老工匠："今天没人来，您怎么不熄灯歇着？"

老工匠笑了笑："因为门卫不知道明天会来什么客人。今天来的都是问数学题的，明天可能全是问历史的。为了随时能接待，我们所有工匠，必须天天到岗。"

这就是城堡最大的开销：6710 亿个工匠的本事，全都要占着地方（显存），可每个客人只用得上其中 370 亿。

城堡的主人算过一笔账：要把 6710 亿个工匠都安置好，需要 1.3TB 的房间——相当于把整座城堡都租下来，可每天只有 5% 的房间真正开张。

账房先生把这笔账念给小词听："6710 亿工匠，每人 2 个字节的档案，就是 1.3TB。一张最好的显卡，也只装得下 80GB。你算算，得多少张卡？"

小词算了半天，没算出来。账房先生替它答："至少 16 张。而且这 16 张卡，每张都得把灯点着，等客人。"

小词又问："那能不能等客人来了，再叫工匠起来？"

账房先生摇头："试过。可门卫没法提前知道明天来谁，临时叫人也来不及——等工匠赶到，客人早就走了。所以所有城堡都认了命：灯，必须全亮着。"

省的是力气，不是房子。

——城堡里所有工匠都会背的一句话

这句话，是后来一切麻烦的开始。

工匠笔记 · 为什么单卡跑不动

一个 token 前向时要读的权重量，除以它要做的计算量，叫算术强度。BF16 精度下这个比值是 1 FLOP/byte——意思是每从显存搬 1 个字节，只做 1 次乘加。

而 H100 这块卡的"拐点"是 295 FLOP/byte：低于这个比值，GPU 就是在等内存，不是在算。两者差了近 300 倍。

所以 batch=1 时 GPU 的算力利用率只有 1–2%。要让 GPU 忙起来，每个工匠手头得攒到约 256 个客人的 batch 才行——这就是为什么生产系统都在拼命做大 batch、做专家并行。

小词后来才明白：这座城堡最贵的东西，从来不是工匠干活，而是让所有工匠都坐在那儿等着。

这也是为什么，后来所有城堡都在拼命做三件事：把客人攒成批（batch）、把工匠分到不同的楼（专家并行）、把工匠的本事压缩成小册子（量化）。三件事，说的都是同一句话——别让灯白亮着。

03

抢客人的风波The Queue Wars

专业导读 · 负载均衡的四代方案

稀疏激活带来一个新问题：门卫会偏心。负载均衡的四代方案，是 MoE 训练史上最实用的一条线——从"往损失里加罚"走到"把均衡从梯度里拿出去"。

  • 第一代 · aux loss（Switch Transformer, 2021）：辅助损失 Laux = α·N·Σi fi·Pi，逼每个专家分到相近比例的 token。有效，但梯度里混进了"为了凑人数而改变分诊"的干扰信号。
  • 第二代 · aux + z-loss（ST-MoE, 2022）：惩罚门控 logits 过大，训练更稳；但损失系数的调参极其敏感，数据分布一变就得重调。
  • 第三代 · aux-loss-free（DeepSeek-V3, 2024）：给每个专家一个偏置 bi，只影响排序、不进梯度；每步按负载更新 bi ← bi + γ·sign(loadi − mean_load)，γ 取 0.001 量级。语言建模的梯度专心学"谁更适合这个 token"。
  • 第四代 · 推理侧（EPLB）：训练时均衡 ≠ 开张时均衡，热门专家在推理时照样被挤爆，于是给它们配冗余副本，并按实时负载动态重排。
  • 反面视角（LLEP, 2026）：适度不均衡不是坏事，专家特化（骨科大夫天天看骨折）本来就是 MoE 想要的；目标不是绝对平均，而是"别让哪个专家排队排到天荒地老"。
  • 结果：V3 用 aux-loss-free 连续训练 14.8T tokens，零不可恢复 spike。

关键论文：Switch Transformer, 2021 · ST-MoE, 2022 · DeepSeek-V3, 2024 · LLEP, 2026

城堡开张没多久，就出了乱子。

门卫的分诊办法有个毛病：他让客人自己挑房间。

客人一进门，自己给 256 个房间打分，挑分最高的 8 个。结果呢？大家都往"名医房间"挤——那几个房间的工匠确实厉害，可再厉害也架不住全城的人都来找他。热门房间门口排起长队，冷门房间的工匠天天打瞌睡。

管家管这叫"负载坍缩"——意思是，城堡白养了一大半工匠。

更糟的是，排队排久了，有些客人等不及，干脆走了——这在城堡的账本上叫"丢 token"（token dropping）。客人丢了，句子就断了；句子断了，城堡说的话就前言不搭后语。

管家想了四代办法。

第一代：贴告示

管家贴了张告示："所有房间客人数量必须平均，不平均就扣工匠工钱。"

这招管用，可工匠们抱怨：为了凑人数，他们被迫接待不对口的客人，活儿越干越糙。有个数学工匠被塞了一堆古诗，气得把算盘摔了。

管家在账本上记下：告示有效，但工匠的手艺退步了。

第二代：再加一条

管家又在告示上加了句："门卫打分别太自信。" 城堡稳了点，可告示的措辞特别难拿捏——客人一多一少，措辞就得跟着改。有一回客人突然少了一半，告示没来得及改，城堡差点又乱套。

第三代：改叫号

来了个新管家，他想了个绝的：

不动告示，改叫号。

他给每个房间配了一个"叫号牌"——忙的房间，号往后挪一点；闲的房间，号往前挪一点。牌子只影响"排到谁"，完全不影响工匠怎么干活。

新管家得意地说："这叫免考核均衡（aux-loss-free）。工匠们该干嘛干嘛，排队的事，交给牌子。"

小词有一次问新管家："牌子上的号，是谁在改？"

"没人改，"新管家说，"牌子自己会动。每个房间忙了，号就往后挪一丁点；闲了，号就往前挪一丁点。挪多少，是算好的——不多不少，刚好让队伍慢慢散开。"

这一招，让城堡创下了纪录：连续训练 14.8 万亿个客人，一次都没崩过。

第四代：配分身

客人真的来了以后，管家发现，就算训练时排得好好的，真开张了，热门房间还是挤。于是他干脆给热门工匠配了个分身——同一个工匠，两个房间同时开工。客人分流了，队伍短了。

分身不是白配的：一个工匠的本事要复制一份，占双份的地方。所以管家只给最挤的几个房间配，而且每隔一阵就重新数一遍队伍，把分身挪到最需要的地方去。

工匠笔记 · 叫号牌的真身

"叫号牌"是每个工匠一个偏置项 b_i。门卫选房间时用 s_i + b_i 排序，但这个偏置不进梯度——它不参与反向传播。

每个训练步结束后按负载更新：b_i ← b_i + γ·sign(load_i − mean_load)。忙的房间 b 减小（下步更难被选中），闲的房间 b 增大。γ 取 0.001 量级。

对比一下第一代"告示"：那是把"均衡"写成损失函数加进去，梯度里就混进了"为了凑人数而改变分诊"的干扰信号。第三代把这个信号从梯度里拿出来了——语言建模的梯度可以专心学"哪个工匠更适合这个客人"。

有意思的是，后来有个学者写了篇论文，说了一句让管家愣住的话：

客人扎堆，其实不全是坏事。骨科大夫天天看骨折，本来就是城堡想要的。

——LLEP 论文（2026）

管家想了半天，把告示又改了：目标不是"绝对平均"，是"别让哪个房间排队排到天荒地老"。

小词后来才懂：均衡不是目的，均衡是手段。真正要保的，是没有一个客人因为排队太久而被丢掉。

04

楼与楼之间Between the Towers

专业导读 · All-to-all 与专家并行

当专家多到一间房装不下，MoE 的瓶颈就从算力搬到了网络。这一章的数字，是整套推理系统设计的起点。

  • 通信量公式：单层 V = 2·T·k·d·b。T=4096, k=8, d=7168, BF16 b=2 → 每层约 939MB；61 层累计约 57GB。系数 2 是"去程 + 回程"。
  • 还没算的部分：路由元数据、padding、对端排队。所以 MoE 推理的瓶颈常常不在矩阵乘，而在网络。
  • EP 而非 TP：张量并行（TP）把每个矩阵切开，每层都要全卡 all-reduce，通信量与向量宽度 d 成正比；专家并行（EP）把不同专家分到不同卡，只在 MoE 层传 token，通信量与"实际被路由的 token 数"成正比——稀疏时更省。
  • EP 的代价：并行度越高，每个专家手头的 token 越少，矩阵乘越小、效率越低。V3 的对策是按阶段换并行度：prefill（成批 token）用 EP32，decode（零散 token）用 EP320——每卡一个专家，靠大 batch 摊薄。
  • 通信库：DeepEP 的两种模式（低延迟 LL / 高吞吐 HT）、NCCL EP、UBEP；NVLink 的 Copy Engine 可以把搬运从 SM 上卸下来。
  • 分离式部署：MegaScale-Infer（attention 与 FFN 拆开）、Step-3 AFD、JANUS（单卡吞吐 4.7×）、FinDEP、NanoCP——把"门诊"和"住院部"分成两栋楼，各自按需扩床位。

关键论文：DeepEP, 2025 · MegaScale-Infer, 2025 · Step-3 AFD, 2025 · JANUS, 2025

城堡越盖越大，一间房不够了，只好盖成 61 层楼。

小词这下惨了。它拿到的 8 张房卡，可能分布在 3 栋楼里。它得从这栋楼跑到那栋楼，敲 3 次门，再跑回来。

跑腿费有多贵？城堡的账房先生算过：

每层楼，跑腿费 939MB。61 层楼，57GB。

——而且这还只是小词自己的行李，没算挂号单和排队时间

账房先生急得直跺脚："这哪是城堡，这是个快递分拣中心！"

小词问："那我能不能只在一个楼里干活？"

账房先生说："不行。8 个房间分散在不同楼，是因为每栋楼只装得下一部分工匠。你要找的工匠，可能这栋楼有、那栋楼也有——你得挨个跑。"

工匠笔记 · 939MB 是怎么算出来的

单层楼、单个 batch 的跑腿量：V = 2 · T · k · d · b。T 是 batch 里的客人数，k 是每人进几个房间，d 是向量宽度，b 是每个数占几个字节，系数 2 是"去程 + 回程"。

代入 DeepSeek-V3：T=4096，k=8，d=7168，BF16 下 b=2——
2 × 4096 × 8 × 7168 × 2 ≈ 939 MB。61 层就是约 57 GB。

这还没算挂号单（路由元数据）、空跑（padding）和对端排队。所以 MoE 推理的瓶颈常常不在矩阵乘，而在网络。

于是城堡开始琢磨一件事：能不能让跑腿和干活同时进行？

传送带

有的楼装了"传送带"，小词在 A 楼干活时，B 楼的工匠已经在准备下一个客人了。这条传送带叫 DeepEP，分两种速度：慢车（低延迟模式）服务零散客人，快车（高吞吐模式）服务成批客人。

慢车的好处是随到随走，坏处是每次只拉几个人；快车的好处是一次拉一大车，坏处是要等车装满。城堡的调度员每天在两者之间切换——白天客人零散，开慢车；夜里客人成批，开快车。

分楼

有的城堡干脆把"门诊"和"住院部"分成两栋楼：看病的楼专门看病，开药的楼专门开药，各自按需扩床位。这叫分离式部署。有个叫 JANUS 的城堡用了这招，单栋楼的吞吐量涨了 4.7 倍。

分楼的好处是：门诊楼的客人来得快、走得快，住院部的客人来得慢、待得久，两种节奏互不打扰；坏处是：两栋楼之间又多了一条跑腿的路。

专用通道

还有的楼，把"跑腿"这件事交给了一条专门的传送通道，连工匠的手都不占——这条通道平时用来搬货（NVLink 的 Copy Engine），闲着也是闲着。

工匠笔记 · 为什么 MoE 偏爱"专家并行"

切分模型有好几种切法：张量并行把每个矩阵切开，每层都要全卡同步一次；专家并行把不同工匠分到不同卡，只在 MoE 层传客人。

MoE 选后者，因为传客人的量和"实际被分诊的客人数"成正比——稀疏时更省；而张量并行的通信量跟向量宽度成正比，每层都跑不掉，跨楼还特别慢。

代价是：专家并行度越高，每个工匠手头的客人越少，矩阵乘越小、效率越低。所以 V3 的对策是按阶段换并行度：prefill（成批客人）用 EP32，decode（零散客人）用 EP320——每张卡一个工匠，靠大 batch 摊薄。

小词后来才明白：城堡越聪明，跑腿的路就越长。它解决一个瓶颈的办法，往往是把瓶颈搬到下一个地方。

05

城堡的十年Ten Years of Moving Bottlenecks

专业导读 · 十年时间线

十年 MoE 史，是一部"瓶颈搬家史"：容量 → 路由 → 通信 → 部署与内存。每一代论文都在回答"这一代什么变贵了"。

  • 1991 · Jacobs：多个专家 + 门控，想法诞生；但没有稀疏训练手段，专家还是全激活。
  • 2017 · Shazeer：top-k 稀疏门控，137B 参数，第一次证明"只激活少数专家"能训得动。
  • 2020 · GShard：600B 参数、2048 台 TPU、4 天训完——MoE 第一次上大规模集群。
  • 2021 · Switch Transformer：top-1 + aux loss，1.6T 参数，把 MoE 变成"可复制的配方"。
  • 2022 · ST-MoE：aux loss + z-loss，稳定性成为一等公民。
  • 2023 · Mixtral 8x7B：开源社区第一次拿到好用的 MoE；专家多但重复干活的问题暴露。
  • 2024 · DeepSeek-V2/V3：细粒度专家 + 共享专家 + aux-loss-free + FP8 + MTP，671B/37B，14.8T tokens 零 spike。
  • 2025 · Kimi K2：1.04T 参数，万亿级开源。
  • 2026 · V4-Pro / K3 / GLM-5 / Qwen3.8-Flash-Next：更大、更稀疏、更省。
  • 三条线：容量线（600B→1.6T→2.8T，稀疏度 4×→18×→56×）；效率线（激活 97B→37B→13B→6B）；部署线（单卡→EP→分离式）。

关键论文：Jacobs 1991 · Shazeer 2017 · GShard 2020 · Switch 2021 · ST-MoE 2022 · Mixtral 2023 · V2/V3 2024 · K2 2025 · V4/K3 2026

小词后来听城堡里的老工匠讲古，才知道这座城堡不是一天建成的。

它是一部"问题搬家史"——每解决一个烦恼，就冒出一个新烦恼。

老工匠坐在壁炉边，一边烤火一边讲。小词搬了个小板凳，听得入了神。

1991：一个想法

有个叫 Jacobs 的人第一次提出"分诊"的想法。他写了一篇论文，说：与其让一个大夫看所有病，不如雇几个专科大夫，再请一个分诊台。可那时候，所有工匠还是都得上，城堡越大越累。想法很好，没人用得动。

2017：只叫两个

一个叫 Shazeer 的人定下了"只叫 2 个工匠"的规矩。城堡第一次真正省了力气，可客人开始扎堆，还老漏号（丢 token）。老工匠说，那几年城堡的账本上，一半是"省下来的力气"，一半是"丢掉的客人"。

2020–2022：开连锁店

城堡学会了开连锁店。6000 亿工匠的城堡，在 2048 台机器上盖了 4 天就盖好了。可楼与楼之间的跑腿，成了新噩梦。老工匠说，那几年城堡里最忙的人不是工匠，是搬运工。

2023：对外开放

Mixtral 城堡对外开放，普通人也开得起小城堡了。可工匠太多，很多人在重复干一样的活。老工匠说，那几年城堡里最常听见的一句话是："这活儿我昨天不是干过了吗？"

2024：把工匠切细

DeepSeek 城堡的管家想出了"把工匠切细 + 留一个全科门诊"的办法——细粒度专家 + 共享专家。这一招，后来被全城的城堡抄了个遍。老工匠说，这是城堡史上第一次"别人来抄我们"。

2025：万亿级

城堡扩到了万亿级。Kimi 的城堡有 1.04 万亿工匠，DeepSeek 的有 6710 亿。可跑腿费也跟着涨到了 57GB。老工匠说，那一年城堡的账本上，跑腿费第一次超过了工钱。

2026：分身术、压缩术、解耦术

最气派的几座城堡——DeepSeek-V4（1.6 万亿工匠）、Kimi K3（2.8 万亿工匠）——学会了分身术、压缩术和解耦术。K3 的城堡有 896 个房间，每个客人只进 16 个，稀疏度 56 倍，是当世之最。

工匠笔记 · 十年演进的三条线

容量线：总参数 600B → 1.6T → 2.8T，稀疏度（总参数 ÷ 激活参数）4× → 18× → 56×。

效率线：每客人激活参数 97B（GLaM）→ 37B（V3）→ 13B（V4-Flash）→ 6B（Qwen3.8-Flash-Next）。

三条线不是并行的，是互相逼出来的：容量涨 → 通信涨 → 逼出分离式部署 → 逼出语义与物理解耦。所以 2026 年的前沿已经不是"怎么更稀疏"，而是"怎么把稀疏的城堡跑得更快"。

老工匠讲完，往火里添了块柴："你看，城堡每解决一个烦恼，就把烦恼搬到了下一个地方。搬到最后，烦恼已经不在工匠身上了——在楼与楼之间，在灯与灯之间。"

小词问："那下一个烦恼会搬到哪儿？"

老工匠笑了："不知道。但我知道，一定会有下一个。"

06

小词的结局Homecoming

专业导读 · 2026 年的四条路线

2026 年的旗舰不再比"谁更稀疏"，而是比"谁把稀疏跑得更快"。四条路线：更大更稀疏、更小更省、更少层、更会省 KV。

  • 更大更稀疏 · DeepSeek-V4-Pro：1.6T 总参数 / 49B 激活，384+1 个专家，top-6，32T 训练 token，1M 上下文；官方称其 FLOPs 只有 V3.2 的 27%。同代 V4-Flash：284B/13B。
  • 更大更稀疏 · Kimi K3：2.8T/104B，896 个专家，top-16，稀疏度 56；扩展效率比 K2 高约 2.5 倍。
  • 更少层 · GLM-5：744B/40B，256 个专家，80 层——刻意压层数，减少跨楼通信。
  • 更小更省 · Qwen3.8-Flash-Next：125B/6B，另有 51B 的 n-gram 表放在加速器外；训练 FLOPs 只有前代的 1/9。
  • 压缩术：MoQE 把专家压到 2-bit；QMoE 把 1.6T 模型压到 160GB（平均 0.8 bit/param）；V4.1-Flash 的 FP4 KV 只占 890 字节/token，1M 上下文才装得下。
  • 哈希路由：V4 的前 3 层直接用 token 编号分专家，连门卫都省了——用"确定性"换掉"学出来的分诊"。

关键论文：DeepSeek-V4, 2026 · Kimi K3, 2026 · GLM-5, 2026 · Qwen3.8, 2026 · QMoE, 2023 · MoQE, 2023 · V4.1-Flash, 2026

故事的最后，小词又走进了一座 2026 年的新城堡。

这座城堡和它第一次进的那座，已经大不一样了。

门口没有门卫。

小词愣了一下，正要开口问，墙上的一块牌子先说话了："前三个门不用我，看你的编号就行。"

小词低头看自己的编号——那是一串它从来没注意过的数字。前三个房间的门，就按这串数字开。这叫哈希路由，只在 V4 的前 3 层用。

小词后来才懂：门卫的分诊是学出来的，学出来的东西会偏心、会排队；哈希路由是算出来的，算出来的东西不偏心，但也不聪明。所以城堡只在最前面三层用它——那三层不需要聪明，只需要快。

城堡分成了两栋楼。门诊一栋，住院部一栋，各自按需扩床位。

工匠们的"本事档案"被压缩成了小册子。每个工匠的本事只占原来四分之一的地方——甚至更少。有的城堡把 1.6 万亿工匠的档案压到 160GB，只占原来 1/20。

小词的"病历摘要"也变薄了。它现在只带 890 字节——是上一代城堡的四分之一。它能在城堡里待上一百万个 token 那么久，也不嫌挤。

小词走出城堡时，回头看了一眼。

它想：这座城堡真奇怪。它明明有 2800 万亿个工匠的本事，却只让每个客人见 16 个；它明明省了力气，却要占 1.3TB 的房子；它明明解决了排队，却又在楼与楼之间堵起了车。

但它还是觉得，这座城堡是聪明的。

因为它把"本事"和"力气"这两件事，分开了。

而所有故事的秘密，往往就藏在这句话里。

工匠笔记 · 2026 年的四座旗舰城堡

DeepSeek-V4-Pro：1.6T 总参数 / 49B 激活，384+1 个房间，每人进 6 个，1M 上下文，32T 训练 token。

Kimi K3：2.8T / 104B，896 个房间，每人进 16 个，稀疏度 56，比 K2 的扩展效率高约 2.5 倍。

GLM-5：744B / 40B，256 个房间，80 层——刻意压层数来减少跨楼通信。

Qwen3.8-Flash-Next：125B / 6B，另有 51B 的 n-gram 表放在加速器外——训练 FLOPs 只有前代的 1/9。

故事讲完了

  1. MoE 就是开一家 256 个专科的医院，但每个病人只看 8 个科室——本事大，力气小。
  2. 它最大的敌人不是算力，是"排队"和"跑腿"——负载不均和跨卡通信，占了 100 篇论文的九成篇幅。
  3. 十年演进就是"问题搬家"——每解决一个瓶颈，就把它推到下一个位置：容量 → 路由 → 通信 → 部署与内存。
  4. 2026 年的分野：不再比"谁更稀疏"，而是比"谁把稀疏跑得更快"——量化、分离式部署、KV 压缩、哈希路由，都是在给稀疏的城堡减负。
  5. 读 MoE 论文的方法：先问"它把瓶颈搬到了哪里"，再看它用什么代价换来了什么。

所以下一次你看到"671B 参数、37B 激活"这样的数字时，可以想起小词：它走进的那座城堡，灯全亮着，而它只敲了 8 扇门。

术语小抄

读完故事，把这 17 个词记住，再去读论文就不会卡住。

专家Expert
MoE 层里一个独立的 FFN 子网络。V3 一层有 256 个路由专家。
路由 / 门控Router / Gating
决定每个 token 去哪些专家的打分网络，也就是故事里的"门卫"。
top-k
每个 token 激活的专家个数。V3 是 8，V4-Pro 是 6，K3 是 16。
稀疏度Sparsity
总参数 ÷ 激活参数。V3 约 18×，K3 约 56×。稀疏度越高，同样算力下容量越大。
共享专家Shared Expert
每个 token 都会经过的那个专家，用来兜住通用知识——故事里那间"全科门诊"。
容量因子Capacity Factor
每个专家最多接收多少 token 的上限。超出上限的 token 会被丢掉。
丢 tokenToken Dropping
专家容量满了，多出来的 token 被丢弃，句子因此断裂。第一代负载均衡就是为了治它。
负载坍缩Load Collapse
token 扎堆到少数热门专家，其余专家闲置——城堡白养了一大半工匠。
辅助损失Aux Loss
逼负载均衡的正则项，加在主损失旁边。有效，但会污染语言建模的梯度。
aux-loss-free
V3 的做法：用不进梯度的偏置 bi 调排序，把均衡从梯度里拿出去。
专家并行EP · Expert Parallelism
把不同专家放到不同设备上，只在 MoE 层交换 token。
All-to-all
token 在设备之间"换乘"的通信模式，MoE 推理的主要开销。
DeepEP
DeepSeek 开源的 all-to-all 通信库，分低延迟（LL）和高吞吐（HT）两种模式。
分离式部署Disaggregated Serving
把 attention 和 FFN 拆到不同机器/阶段（MegaScale-Infer、Step-3 AFD、JANUS），各自按需扩容。
KV cache
